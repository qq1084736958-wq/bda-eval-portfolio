## 1. 这个产品解决什么问题

管理者查经营信息时，常要在报表、台账、采购数据和制度文件之间来回切换：指标依赖人工筛选易遗漏，制度解释易引用旧版本，不同角色可见范围和金额精度不同，而 AI 即使没有依据也可能"一本正经地编"。

**产品目标**：让管理者用自然语言获得"**有权限、可追溯、知道下一步**"的经营信息。

| 用户 | 典型诉求 | 示例问题 |
|---|---|---|
| 高管 | 看全局、看趋势、看重点项目 | "今年采购金额最高的 5 个项目是什么？" |
| 部门经理 | 管本部门预算与项目 | "我们部门二季度采购金额按月看。" |
| 项目专员 | 查项目、理解口径 | "采购金额是否包含暂估金额？" |
| 运营管理员 | 维护问答质量与知识 | "哪些问题因为无依据被拒答？" |

## 2. 产品处理链路

```
用户自然语言问题
   → 意图识别（经营数据 / 制度知识 / 上下文追问 / 复合问题）
   → 权限与数据范围校验（角色决定可见部门与金额精度）
   → 结构化数据查询  /  知识库 RAG 检索（按意图门控，该查才查）
   → 回答 + 数据口径 + 来源引用 + 下一步建议（无依据则明确拒答，不编造）
   → 可追溯 Trace / 未知问题回收 / 用户反馈 → 持续迭代
```

详见 [产品概述](docs/产品概述.md)。

## 3. 我搭建的评测体系（核心）

一个会聊天的系统不等于能上生产。企业场景里错一个口径、漏一条权限、编一个结论都直接影响决策。所以我设计并落地了一套 **可复现、可追溯、能驱动迭代** 的评测：

**① 数据集 = 标注集 + 真实问题回流**
从运行库的**未知问题池 / 用户反馈 / 问答日志**回流真实提问，去重分桶标注后扩充——评测集来自真实用户，不是拍脑袋编的。

**② 两层指标，各司其职**
```
确定性层（规则自动判定）： 路由 / 状态准确率 · RAG 引用命中 · 结构化取值正确   → 可复现、无主观
质量层（LLM-as-Judge）：  正确性 / 清晰度 / 依据充分性 / 可行动性 / 表达自然度   → 每维≥3 且均分≥4 记 PASS
```

**③ 评审设计**：答案由被测模型生成，**评审换一个不同家族的模型**（降低自评偏好），复用产品既有五维 rubric 与阈值。

**④ 回归基线**：固定数据集与口径即为基线，改版后重跑，指标退化即暴露。

👉 **完整方法、真实基线与发现：[评测体系设计与发现](docs/评测体系设计与发现.md)**

## 4. 评测驱动的发现（节选）

- **口径歧义是头号真实痛点**："采购金额是否含暂估金额"同时出现在 评测失败 + 未知问题池(复现 4 次) + 用户差评(标记"数值不一致") 三处 → 建议把高频口径固化为知识点并在金额答案中主动回显。
- **制度/招标知识覆盖不足**：招标阈值、采购方式等多条 RAG 题失败且在未知问题中反复出现 → 按频次优先补齐制度文档与别名映射。
- **多轮追问稳定性缺陷**：评测中定位到一个真实崩溃 bug（上下文继承空值）→ 修复并纳入回归。
- **最弱维度是"依据充分性"(4.15)**：答案有时结论对但来源/口径展示不足。

## ⚖️ 诚实边界

- 数据为**可重复生成的模拟数据**，用于验证链路与口径，非真实企业数据。
- 质量分来自**自动 LLM 评审，尚未与人工分数校准**；建议抽样人工对齐并报告一致率。
- 所有指标均标注数据集规模、被测/评审模型与日期；未执行的指标不写成真实准确率。
