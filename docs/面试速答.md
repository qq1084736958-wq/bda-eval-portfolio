## 0. 统一口径

**一句话定位**：面向企业管理者的可控 AI 经营问答——用自然语言查经营数据与制度知识，系统在权限范围内返回"有结论、有依据、有权限边界、知道下一步"的回答。

**我的角色**：AI 产品经理（实习）——参与需求定义与产品设计，**独立设计并实现了评测体系**（真实问题回流、两层指标、自动 LLM-as-Judge、回归基线），运行真实基线并产出优化清单；产品工程由团队协作完成。

**边界**：本地演示、模拟数据、离线评测；不声称真实企业上线或业务增长。

**60 秒介绍**：我做了一套面向经营数据与企业制度查询的可控问答产品。它不是把问题直接丢给大模型，而是用 AI 处理自然语言、语义检索和表达，用数据库与规则保证金额、权限、版本和引用可靠。打通了手机端与运营后台，并通过 80 条标注用例的离线评测（路由准确率 95%、质量 4.58/5）发现复合路由、上下文和口径等问题，再针对链路节点修改和回归。

## 一、项目与定位

**Q：为什么做这个项目？**
经营查询要求用户记入口、指标名、筛选条件和制度文件位置，跨数据与制度时还要自行判断是否同口径。回答错了会有决策、合规、信任和重复沟通四类成本。我想验证：能不能用一条**可追溯、权限受控**的问答工作流，让管理者直接拿到可信结论。

**Q：为什么必须用 AI？普通搜索/BI 不行吗？**
用户表达有错别字、别名、上下文省略、复合意图和语义检索需求——这些是 BI 的固定报表和关键词搜索处理不了的。但我**只让 AI 处理模糊性**，金额、权限、版本这些确定性信息交给系统。

**Q：这算 Agent 项目吗？**
它是**固定 Workflow（确定性编排）**，不是开放式多 Agent。当前任务路径稳定，可预先拆成识别/查询/检索/校验/展示等节点，Workflow 成本更低、延迟可控、每个节点可 Trace 可评测。只有未来需要跨系统开放式规划、动态选工具时，才引入 Sub-agent / Agent Team——我不为技术包装增加不必要的复杂度。

**Q：为什么不把所有问题直接交给 DeepSeek？**
经营数值和权限是高风险确定性信息。让模型自由推断，回答可能流畅但无法保证数值一致、不越权、制度版本正确。所以边界是"**AI 处理模糊性，系统处理确定性**"。

## 二、产品设计

**Q：为什么设计四类账号？**
高管/部门经理/项目专员/运营管理员的数据范围与金额精度不同。四类账号用于验证权限不是"登录/未登录"开关，而是**角色、部门、项目、字段精度的组合**。

**Q：为什么既做手机端又做后台？**
前台完成用户任务，后台形成闭环：日志、未知问题、反馈、知识库、Prompt、权限、评测。没有后台，问题只能靠感觉改；有后台，才能把失败归因到节点并回归。

**Q：失败提示为什么是核心能力？**
正确拒答只是安全底线。我把失败拆成条件不完整/无数据/无依据/无权限/未支持/异常六种状态，各配原因码和下一步动作——**让用户知道为什么、以及接下来怎么办**，这才是产品体验。

**Q：如果只能保留一个功能？**
保留"**带权限和引用的可追溯回答**"。可追溯和权限边界是企业场景的信任底座，比多一个图表类型重要得多。

## 三、技术链路

**Q：完整链路是什么？**
问题归一化 → 任务路由（结构化/RAG/复合）→ 任务规格化 → 权限过滤后的结构化查询 / metadata 过滤+召回+重排的 RAG → 确定性数值与来源校验 / 受控回答生成 → 答案组合与失败状态映射 → 展示 + Trace → 评测/回归。

**Q：结构化查询为什么不能也用 RAG？**
金额要精确计算、聚合、排序，并严格受权限约束。RAG 适合语义检索制度文本，但不该用来"算钱"——否则会有口径漂移和金额幻觉。

**Q：如何防止引用过期制度？**
RAG 在**检索前用 metadata 过滤**（启用状态、当前版本、生效/过期日期、权限），不是在页面隐藏。先过滤可访问且有效的文档，再召回重排取 Top 5，答案强制绑定 chunk 引用。

**Q：没检索到可靠内容怎么办？**
走"知识库无依据"状态，**拒绝给确定性结论**，提示换问法或反馈补文档——绝不用模型常识补企业制度。

**Q：多轮追问怎么实现？**
不是存聊天气泡，而是存**可执行的任务规格**（指标/部门/项目/时间/维度）。追问"按项目排一下"时保留上一轮规格、只覆盖本轮明确修改的字段，并在换项目/换域时清理旧字段。

**Q：复合问题怎么处理？**
拆成业务与知识两个子任务，分别做权限过滤与执行，再组合成**双来源答案**分区展示。这是早期 0/5 通过时发现的架构级问题——不能只改 Prompt。

**Q：为什么要做 tracing？**
每次问答写 `traceId`，记录路由、意图、指标、权限规则、来源与状态。失败时能**定位到具体节点**，而不是笼统"优化 Prompt"。

## 四、评测与成果

**Q：你的评测怎么做的？**
两层：确定性层用规则自动判路由/状态/引用/取值；质量层用 LLM-as-Judge 打五维（正确性/清晰度/依据充分性/可行动性/表达自然度）。评测集里加入**从未知问题池/反馈/日志回流的真实问题**，并建回归基线。评审模型刻意换成与被测不同的家族，降低自评偏好。

**Q：真实指标是多少？**
80 条标注用例、被测 DeepSeek-V3.2：路由准确率 95%、状态准确率 92.5%、RAG 引用命中 87.9%、结构化取值正确 100%；答案质量五维综合 4.58/5、通过率 87%，最弱维度是依据充分性（4.15）。

**Q：如果基线不高，是不是产品很差？**
第一轮完整评测的价值就是**暴露结构性缺口**（比如复合问题早期 0/5、上下文 40%）。亮点不是隐藏低基线，而是用 trace 把失败定位到路由和状态机制，修改后对失败项回归。评测中我还**定位到一个真实崩溃 bug** 和一条贯穿"评测失败+未知问题+用户差评"三处的口径歧义。

**Q：你到底做了什么？（角色边界）**
需求定义与产品设计我参与；评测体系（真实问题回流、两层指标、自动 LLM-as-Judge、回归基线）是我独立搭建并运行的；指标我能说清样本量、判定标准、被测/评审模型与日期。产品工程由团队协作完成，我不虚写"独自开发全部代码"。
